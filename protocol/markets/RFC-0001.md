# RFC 0001 — GHOST Markets, privacy-native market execution

Date: 2026-11-26  
Status: proposal, not implemented on-chain  
Owner: GHOSTRINGS (independent project)  
Repository: https://github.com/ghostrings/zolana

## Summary

Separate the ring policy program from the market application program. Use the official, compatible Custom Ring implementation as the policy and audit authority, and develop an application-specific market program around approved proof interfaces. Do not fork core cryptography merely to create a program address. Design token issuance, launch curve, migration, pool and position accounting, and atomic trade settlement as separately reviewed components.

Market execution should not require a public Meteora swap for every confidential fill. This RFC does not implement confidential settlement, custody, a relayer, private trading, a private AMM or asset creation. The initial implementation is public deterministic pricing arithmetic only.

## Protocol boundaries

| Component | Responsibility | Status |
| --- | --- | --- |
| Existing privacycash.fun | Public Meteora execution and existing Default Ring wallet | Existing; unaffected |
| GHOST market math | Public integer curve and pool quote arithmetic | Node reference locally tested; Rust reference uncompiled |
| GHOST Markets program | Market configuration, mint lifecycle, issuance, reserves, fees, position accounting, proof-bound market transitions | Proposed |
| GHOST Custom Ring | Supported upstream ring program, required authorization and audit controls | Not generated, deployed, initialized or activated |
| Solana Privacy Program | Authoritative encrypted notes, vaults, nullifiers, ZK verification | Upstream base protocol |
| Intelligence | Public supply, declared insider allocations, audit attestations with scoped coverage | Proposed for new market |

A program deployed on Solana does not automatically become a recognized ring. Registration and activation are distinct. Where governance activation is required, an inactive ring must reject private movement. Program upgrade authority and auditor key custody must be independently reviewed. No permanent delegate is proposed.

## Privacy contract

Initial production candidate, if eventually approved, must disclose mint, token metadata, supply, fee policy, creator/related-party allocations, material market controls, reserve and price information appropriate to the chosen market design, and all public settlement boundary information. Financial details may be protected only to the extent supported by the verified ring and settlement proofs. Public reserve changes may reveal individual trade sizes; public supply and token account data remain public. Relayer, prover and auditor visibility must be clearly disclosed.

A native shielded market is not automatically a private blockchain. Neither zero-knowledge proofs nor an auditor proves common beneficial ownership across arbitrary wallets. Do not claim anonymous creators, hidden bundles, unobservable market manipulation, or guaranteed private trades. Do not use privacy to mislead market participants about supply concentration or related-party activity.

## Market lifecycle

1. **Create market:** commit token mint and issuance terms, fee policy, declared issuer allocation and graduation rule in public metadata; reject changes that violate immutable commitments.
2. **Launch:** provide a deterministic curve and bounded real inventory. Virtual reserves affect quote calculation but cannot be withdrawn. Define exact rounding, slippage bounds, maximum supply and fees in base units.
3. **Graduate:** explicitly account for every token, reserve and outstanding fee before initializing the post-launch pool. Use an atomic, authorized, once-only transition; no double migration or hidden creator allocation.
4. **Pool:** use separately validated constant-product or other agreed pricing, auditable liquidity accounting and LP share conservation. Deposit/withdrawal and LP pricing require independent specifications; they are not implemented by the quote function.
5. **Settlement:** supported proof and authorization interfaces must bind the exact market and asset pair, state version, quote, fees, expiry, consumed/created notes and authorized outputs to one atomic transition. The market must not update state if settlement fails. No real-fund path is allowed until proof composition is validated.
6. **Reporting:** publish accurate market-level totals and scope, including known related-party allocations. Audit-derived reports must state coverage, snapshot slot, attestor, limitations and privacy controls. Missing evidence is unknown, not zero.

## Pricing reference

For real reserves `X`, `Y`, virtual offsets `Vx`, `Vy`, gross exact input `d`, and fee rate `b` in basis points:

- Effective reserves: `x = X + Vx`, `y = Y + Vy`.
- Fee `f = ceil(d*b/10000)`; net `n = d-f`.
- Output `q = floor(y*n/(x+n))`.
- Proposed next real reserves: `X' = X+d`, `Y' = Y-q`.

Both implementations reject invalid sizes, overflow, zero output, unmet minimum output, fees consuming the entire input, and any quote that would spend the last unit of actual output reserves or consume virtual inventory. Fees remain in the input reserve for this narrowly scoped model. The chosen offsets must be fixed for any proof-verified pricing transition; they are not arbitrary per-trade user inputs in a future on-chain program. A full launch curve, graduation and liquidity operations are not implemented here. This is not Meteora-compatible pricing or a recommendation to use this math with real funds.

Public reserve arithmetic is deliberately chosen for the first implementation because it can be checked without crypto assumptions. A future market that commits to encrypted reserves requires a separate formal design, verifiable state transitions, proof-system security, availability, pricing disclosures and audit review. It is outside the scope of this implementation.

## Supported upstream integration

Consult the official repositories and confirm compatible program ID, release tag, SDK, verification keys, proof schema, Ring RPC and cluster before generation. Do not mix the template revision with a different deployed service version.

- [Custom Ring reference implementation](https://github.com/helius-labs/custom-privacy-rings) — ring authorization and policy, ring RPC custody and activation limitations. The README available on 2026-11-26 describes `new`, `deploy`, and `init`, including separately provisioned role keys. `init` registers with SPP; registration does not prove activation.
- [Official generator](https://github.com/helius-labs/zolana-ring) — generated source and revision-pinned interface. Confirm the correct template and operator versions with Helius; the repositories are moving independently.
- [Proof composition](https://github.com/helius-labs/custom-privacy-rings/blob/main/docs/design/proof-composition.md) — the ring and SPP proofs bind shared values. Market-specific correctness is an additional requirement.
- [Privacy Ring examples](https://github.com/helius-labs/privacy-ring-examples) — reference for confidential swap/escrow interfaces only. Its README explicitly says example proving keys are insecure and the programs must not be deployed or used with real funds.
- [Architecture](https://www.helius.dev/docs/privacy/concepts/architecture) and [overview](https://www.helius.dev/docs/privacy/concepts/overview) — privacy guarantees, ring and application responsibilities.
- [Security](https://www.helius.dev/docs/privacy/security) — as viewed 2026-11-26, Custom Ring audits expected to conclude December 2026.

No claims are made about specific third-party ring registrations or live governance state; these were not independently verified. Do not assume that Plaza's deployment proves support for this protocol or that third-party approval is transferable.

## Go/no-go milestones

| Gate | Evidence required |
| --- | --- |
| G0 public arithmetic | Unit and invariant tests in JS and Rust, cross-implementation vectors; no chain claims |
| G1 official ring compatibility | Maintainer-confirmed version, cluster, program and verifier artifacts; reviewed key custody and policy |
| G2 local validator | Actual ring generation/build; real positive and negative proof tests, activation and pause checks, reproducible binary hash |
| G3 devnet | Executable program with verified owner, upgrade authority, config, registration and activation; actual devnet settlement receipt; no customer funds |
| G4 market program | Reviewed mint/curve/pool account model, atomic proof-bound settlements, race/replay/overflow/failure tests, disclosed allocations |
| G5 security and governance | Independent audit including market-specific proofs, correct approved keys, lawful operating model, documented emergency exits and authority separation |
| G6 production | Authorized activation where required, independent binary/config verification, staged release and monitoring; explicit production approval |

For every release, publish **separately**: cluster, source revision, build artifact hash, program address, upgrade authority, ring registration, activation state, review/audit status and independently verifiable successful test evidence. Never equate an executable program account with successful private trading. An inactive registration is not production readiness.

## Initial maintainer questions

- What exact ring program release, template and SDK are supported for new devnet integrations today?
- Which approved proof interfaces support program-owned notes and market settlement, and what constraints apply to atomic multi-leg settlement?
- How should application-defined state transitions be bound to the supported SPP proof without weakening the core protocol checks?
- What are the expected security review, activation and operational requirements for confidential markets with explicit market integrity and audit controls?

This RFC proposes a reviewable public pricing module and design discussion. It is not a request to bypass activation or a claim that a program has already been deployed.
